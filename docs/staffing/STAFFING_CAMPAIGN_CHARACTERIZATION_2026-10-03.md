# Staffing characterization on historical and disposable local environments

This increment adds executable evidence for existing campaigns, manager cancellation and direct matrix persistence, without changing production handlers, migrations, counting, authorization or request vocabulary. It follows the [Phase 0 map](STAFFING_PHASE0_BEHAVIOR_MAP_2026-09-30.md), after [PR990's production rollout](PR990_PRODUCTION_ROLLOUT_2026-10-03.md).

## Reproduce

Start the private historical stack described in its local `README.md`, then run from the repository in PowerShell:

```powershell
./scripts/test-staffing-edge-local.ps1 -CredentialsPath C:/Users/Javi/AppData/Local/AreaTecnica/dev-history/status.env
```

The path contains local demo keys and remains outside Git. The runner restores its process environment afterward and runs the four runtime suites sequentially. `-TestFile` accepts one or more suite paths for a focused reproduction. The suites reject hosted URLs, non-demo credentials, external routing, additional runtime/database/capture networks, stale copies of the invoked handlers, and an unavailable private drain protocol. A TypeScript AST walk follows local imports/re-exports from orchestrator, sender, cancellation notifier and push (87 modules), plus Flex for matrix cases (90). One argument-based, NUL-framed Docker read checks every source path and body. Sixty-eight regular unit tests cover refusal paths, framing, a matching-source positive control, filesystem access under jsdom, cleanup ordering, transport observation, runtime fencing and navigation before/after the fixture month. Three stale-sender cases failed against the original six-module gate and passed after expanding it. The activity-cleanup control failed against the original ordering and passed after moving cleanup before the remaining-job assertion.

The runtime suites use real local GoTrue authentication, JWTs, Edge Runtime, Supabase JS, PostgREST, SQL RPCs, constraints and triggers. The original fetch transport is passed explicitly because the ordinary unit-test setup replaces global fetch before each test. UI tests replace only client bindings; the hooks, dialog, QueryClient and persistence services stay real. Synthetic identities and jobs are owned by each run. Providers are captured inside the isolated network; no email/WhatsApp is delivered externally. Automatic availability waves are disabled, so no historical candidate is contacted. Automatic offer handoff uses only synthetic candidates.

The private local Auth service issues ES256 user sessions. Its router now validates those sessions through that same isolated Auth service, while retaining HS256 validation for legacy demo API keys and each configured handler exposure flag. The original router rejected a real manager session with 401; after correction the same missing-tuple probe reached the handler's 404, while tampered signatures and malformed credentials still returned 401. This is a local environment correction, not a production JWT configuration change or evidence of production user-session compatibility.

Cleanup removes owned jobs, job-scoped inbox notifications and activity records, and synthetic users. Push attempt rows cascade with owned inbox items. Activity has no cascading job FK, so deletion explicitly covers it after job/assignment deletion and before checking whether any fixture job survived. Every user deletion is attempted even after another fails, and restoration checks still run. Before/after ordered row fingerprints cover jobs, staffing requests, assignments, timesheets, profiles, activity, notification inbox and push delivery attempts. Local Auth session/provider capture logs and tables outside that list are not part of the comparison.

The UI suites observe and await actual SDK function calls before cleanup. Completed HTTP error responses are distinguished from transport failures. HTTP completion alone does not establish server completion: the real Flex and sender handlers schedule deferred work through `EdgeRuntime.waitUntil`. Each suite verifies the private runtime fence before taking its baseline or creating users, and every cleanup acquires a drain acknowledgment before SQL deletion. Cleanup is marked unsafe before waiting. A transport or drain failure retains owned fixtures and stops subsequent fixture creation; quiesce the isolated runtime before manual recovery. The tracker does not abort a handler merely to make teardown finish.

Private local instrumentation tracks active handlers and registered `waitUntil` promises for modern `Deno.serve` and legacy `Deno.serveHttp` workers. Drain acknowledgments verify worker boot identities and invocation IDs, repeat when request admission/dispatch changes, and include nested internal calls. A lease blocks external function admission throughout owned SQL cleanup; it is released only afterward. Monotonic deadlines reject a late acknowledgment even if transport ignores its abort signal and prevent new cleanup mutations after the cleanup budget expires. Drain/cleanup/release budgets are 40/45/5 seconds, inside 100-second per-test teardown; final teardown allows 200 seconds for two fenced cleanups and preservation checks. Concurrent cleanup and release failures preserve both errors, including retained user IDs. A completed SQL denial or preservation assertion remains retryable after proven drain/release, so final teardown can still remove owned Auth users. Every SDK client observes the full cloned response body before interpreting a result: network or body-read failures independently latch uncertainty, while completed SQL errors do not. UI teardown retains uncertainty from either SDK observation or the runtime fence. Separate retained-job and retained-user guards block new fixtures until each failed cleanup succeeds; a successful job cleanup cannot clear a failed user cleanup. Concurrent campaign API requests remain allowed for the held-lock test. Removing the retained-state guard made its mutation-refusal control fail. Removing the retry classification made the surviving-job control fail; accepting headers without the body made the interrupted-body control fail.

The protocol is configured outside Git in the private local stack. Two actual-runtime cases verify HTTP response before deferred marker completion, cleanup waiting for the task, and admission remaining closed through cleanup, for both serving APIs. A separate database-free disposable runtime also passed nested work on a reused worker, admission paused before worker creation, tracked rejection, native worker shutdown, caller timeout and caller abort controls. Removing deferred-task registration made the real probe fail because drain acknowledged too early; restoring it made the controls pass. An independent Astra design review and a separate implementation review informed these controls; measured behavior provides the evidence. The protocol does not prove delivery success when a handler catches a provider error, nor does it cover arbitrary unregistered detached work or automatic recovery after a killed test process.

Campaign HTTP calls also track pending requests and latch transport/body-read failures. Their 40-second client timeout does not establish server completion: cleanup and new fixture creation remain blocked even after another call succeeds. Both teardown hooks and the next test's setup enforce the guard. The concurrent-tick case releases its held lock and awaits the winner in `finally`, including after an assertion failure. Unit controls cover pending concurrent requests, timeout/network failures, completed HTTP denials and the actual harness mutation/cleanup boundaries. Calendar navigation derives direction and distance from the rendered caption, so dates after October 2027 can navigate backward without changing the clock used by real authentication. Removing the harness guards made its timeout control fail; restoring forward-only navigation made both future-month controls fail. All forty-six checks passed after restoration and the fence deadline fixes. These unit/calendar negative controls do not mutate the historical database; deferred-task negative controls run only on the database-free disposable runtime.


## Disposable-clone reproduction and safety

A separate runner exercises partial-write faults and public capability links against a faithful, masked disposable clone:

```powershell
./scripts/test-staffing-disposable-local.ps1 -CredentialsPath C:/Users/Javi/AppData/Local/AreaTecnica/dev-history/status.env -ManifestPath C:/Users/Javi/AppData/Local/AreaTecnica/dev-history/release-pr990/matrix-fault-clone-state.json
```

Provisioning and credentials remain private. The manifest describes a separately labelled clone with seven services, five fresh Docker volumes, an internal network and one loopback gateway. Admission checks live ownership, exact networks and mounts, and plain local volume storage without backing options. A label alone is insufficient: local bind-backed or remote-driver volumes are rejected. API and fault SQL use the same frozen target; SQL names the container's local PostgreSQL socket explicitly. Every SQL call receives the current fence guard and rechecks it after Docker inspection, immediately before launching `psql`. A control that exhausts the deadline during inspection refuses SQL and permits retry under a fresh fence; removing that check makes the control fail. The persistent historical harness remains a fixed entry point without fault injection. Both runners use the same source, transport and runtime-fence implementation.

The matrix suite lazily installs a temporary trigger on `timesheets`, backed by a private schema. Its privileged lookup has an empty search path, fully qualified relations and no schema/table/function access for public API roles. Actual privilege metadata is checked. Only the current run's owned job, technician, manager caller and selected date can activate the fault. The job title and private schema comment also carry the owned marker. Fault configuration is cleared inside fenced cleanup before owned jobs are removed; retirement requires a matching schema marker and zero fault rows. Existing guards require manual recovery. A failed Docker SQL driver latches uncertainty and retains fixtures; its control also checks that the wrapper exposes the live cleanup-safety getter.

Each disposable suite compares eight clone tables and the same eight original historical tables before/after cleanup. These comparisons cover the named tables, not every database catalog or Auth session. This temporary local privileged test fixture warrants deliberate maintainer review. It is not a production migration and does not modify production functions or grants.

Seven integrated negative controls rejected disabled fault injection, sequential date RPC dispatch, a delayed erroneous dialog close, unsafe volume backing, a mutating HEAD handler, an inert GET handler and a missing post-inspection deadline check. Temporary source variants were restored byte-for-byte; both eight-table baselines were unchanged and the fault guard was removed. Handler variants ran only in the owned clone runtime.

## Cases and observed contracts

The campaign suite contains 27 actual-runtime cases:

- Management authentication for creation; technician/missing-auth denial; service-only tick.
- Assisted creation remains idle without a tick; auto creation immediately ticks with waves disabled. Start returns its pre-tick snapshot, so persisted state is checked separately.
- Invited membership counts as filled without schedules; declined membership does not. A completed campaign rejects further ticks.
- Pause and paused nudge do not tick; resume and active nudge do. Paused/stopped/completed resume synchronizes new required roles; active/failed resume is rejected.
- Fresh run locks reject ticks; stale locks and locks with no timestamp are reclaimed by direct tick. A real PostgreSQL role-row lock holds the winning tick while another actual runtime request receives 429. This is a held-lock interleaving, not two simultaneous initial compare-and-swap reads.
- The sweeper selector excludes a due stale-locked campaign. The same campaign is selected when unlocked, then direct tick recovers the stale lock. **CARLOS A3 remains unfixed**: sweeper selection prevents automatic crash recovery even though direct tick supports it.
- Offer direct role takes precedence over send-event metadata; availability uses the latest role-bearing send event. Repeated date rows count one profile, and missing role metadata does not create a role count.
- Latest availability role metadata drives a real automatic offer handoff through the sender. A same-job declined offer in another role blocks handoff; an expired-offer control permits it.
- Remaining offer capacity and response ordering select one earliest eligible profile, rather than counting date rows. A replay respects the pending offer reservation.
- Accepted offers without membership retain capacity across repeated ticks despite error events. Matching invited membership fills the role without double counting; expiring the offer or increasing demand permits another synthetic candidate's offer. These fixtures characterize recovery consequences, not the manager UI or an automatic retry policy.

The tests preserve the current odd outcomes. In particular, invited-as-filled and accepted-but-unassigned reservations are not silently corrected. Positive/negative fixture controls distinguish invited/declined, fresh/stale, locked/unlocked, direct/metadata role and declined/expired behavior. Independent review identified activity cleanup, all-user cleanup and an empty-selector false-positive gap; these were corrected before final verification.

The cancellation suite adds eight cases (P0.13): both phases expire pending/confirmed/declined rows across dates but leave already-expired rows and other tuples unchanged; replay returns zero-row success and sends another successful notice; a technician gets zero-row RLS success but both notifications return the expected 403; a missing tuple still reports hook success while the notifier returns its exact 404; active staffing query data refreshes and the update event fires; the latest original channel selects captured WhatsApp delivery; cancellation preserves existing assignment and schedule rows. Notification events alone are not treated as delivery success: actual function responses and the hook's separate push call are checked.

The matrix suite adds eight cases (P0.14/15/17): inclusive Madrid dates spanning a UTC date boundary; exact single-day confirmed coverage; sparse multi-date coverage including an earlier prep day; adding dates without downgrading confirmed membership or changing its scoped anchor; retained approved work/approval/signature inputs; replacement coverage; single-date removal retaining membership and other dates; last-date removal deleting membership through the lifecycle RPC; and technician denial by the actual date RPC. Several contracts are combined in one case. The actual calendar, role selector and dialog are exercised. The approved-row assertion deliberately excludes derived category/rate fields: the real category-sync service may recompute those. Partial-write failures are not injected into the persistent historical database.


The disposable matrix suite adds three cases (P0.16): a sparse-date success control; one real failed date RPC after membership commits, preserving membership and the successful date while retaining the open dialog without success/Flex/push/update effects; and exact technician authorization denial. Native SDK transport records membership response-body completion before either date RPC and overlapping dispatch of the two date calls. This establishes client dispatch order, not simultaneous PostgreSQL execution. The failure assertion keeps the real component mounted beyond its 100ms close window and drains observers again.

The disposable public-method suite adds fifteen availability cases (P0.21/CARLOS A1). Legacy query and path links leave valid HEAD requests inert; GET and POST URL credentials record confirm/decline once, with opposite-action replay unchanged. Valid fixture credentials expire thirty days after the current time, so they remain valid after 2028; the expiration case retains its explicit past expiry. Invalid and expired GET credentials are inert, and POST body credentials alone are ignored. Calls omit caller Authorization and never follow external redirects. The isolated result-page probe produces inline fallback HTML; these tests do not establish browser navigation, offer acceptance or every HTTP method. They preserve the existing mutating GET behavior; CARLOS A1's product fix remains pending.

## Limits and remaining roadmap work

The runtime suites are **opt-in local evidence**. Ordinary CI runs sixty-eight safety/cleanup/observation/calendar/fence/clone controls and reports these 63 runtime cases as skipped; a skipped suite is not runtime verification. Reproduction requires the private stack's drain protocol as well as copied handler source. CI provisioning of an isolated Auth/Edge/capture stack remains separate work. The existing CI PostgREST acceptance/lock and pgTAP suites continue unchanged.

This closes the named campaign, cancellation and direct-write happy/removal slices, not the entire Phase 1 exit gate. Still missing here: automatic availability-wave ranking/size/deterministic keys and cross-job decline selection (P1.1/10/12), two simultaneous initial CAS contenders (P1.7), and exact completion-push count/failure controls (P1.14). Offer public-method behavior, browser result navigation, full TTL/cancellation semantics, failure fencing and transactional capacity/conflict checks remain later boundaries. No stale-lock recovery or other production behavior is changed by these tests.

Rollback is removal/reversion of the test harness, runner and documentation. No production database push or Edge Function deployment is required for this increment.
