## Roadmap contract decision

The [Phase 0 behavior map](STAFFING_PHASE0_BEHAVIOR_MAP_2026-09-30.md), sections 14–16, requires characterization before changing a boundary and asks whether one transaction should own assignment and timesheet creation. PR990 implements that narrow boundary for accepted offers. It does not consolidate direct assignment writers or complete the staffing overhaul.

The intentionally changed P0 case is **9: timesheet upsert failure after assignment creation**. `preservedMutationContracts.test.ts` previously expected the membership to remain; it now expects no new membership and no new schedule. An existing membership, its metadata and trigger effects also roll back if any schedule write fails. `staffing-phase1-characterization.test.ts` now identifies one command after the committed response instead of separate membership and schedule writes. Actual SQL and HTTP tests verify that command rather than relying on source inspection or the in-memory transaction fake.

The response still commits first. Conflict or persistence failure therefore retains a confirmed offer with no successful assignment. The user-facing response continues to acknowledge the recorded response, as before. This phase does not redefine a confirmed offer as guaranteed assignment success.

The following contracts remain: availability does not assign; sender persistence precedes delivery; request vocabulary, campaign counting definitions and role scoping are unchanged; active timesheets remain date-level coverage; offered date consent stays frozen; existing confirmed membership scope stays intact; dryhire skips timesheets; tourdate creates schedule-only rows; Flex remains best-effort outside the transaction. **Campaign outcomes can change:** a timesheet failure now leaves no new membership and therefore retains an accepted-but-unassigned pipeline reservation; see recovery below. Assignment success events, assignment push and Flex are issued only after the RPC succeeds. The earlier response notification remains outside and before that command.

Only the production `staffing-click` Edge Function changes in this PR. Sender changes are confined to the shared test harness. The additive `assign_staffing_offer` RPC is invoker-security and executable only by `service_role`; the handler retains responsibility for credential verification, accepted dates and the existing conflict check.

## Remaining roadmap work and operational limits

The staffing advisory lock serializes acceptance and the timesheet-removal RPC for their job/technician pair. Direct assignment writers do not share that lock; the pre-existing missing-row/upsert scope race with those writers is not solved here. Conflict and capacity checks are not transactional across different jobs or technicians. Request cancellation, campaigns, wider lifecycle semantics, external retries and their P0/P1 cases remain separate roadmap boundaries. This report does not claim every Phase 1 exit criterion is completed.

Responsible-role membership triggers that update profiles, and changed-actor auth-user FK checks, retain pre-existing transaction risks. This PR's closure is scoped to introduced assignment/schedule lock lifetimes, not every deletion path in the system. A concurrently deleting attribution profile makes acceptance fail atomically rather than wait in a deadlock.

Confirmed responses whose assignment fails still require management follow-up. Repeating the answered link does not retry assignment. The prior manual recovery path remains; no retry/outbox protocol is introduced.

### Accepted-but-unassigned recovery

The additional PR review correctly identifies an operational consequence: the unchanged orchestrator counts a confirmed, role-attributed offer without assignment as `acceptedOffersNotAssigned`. That reserves pipeline and offer capacity indefinitely while the request retains that state. A schedule-write failure now rolls back membership and can create this reservation; before PR990 that failure could leave membership counting as assigned. The error events do not release the slot. Automatic retry, releasing reservations and manager alerts are **not implemented** here; P1 case 15 in the behavior map now tracks their characterization and recovery policy.

Use the read-only [recovery queries](../../scripts/sql/staffing-acceptance-recovery.sql) after deployment to identify recent confirmed offers missing membership or known single/batch-date coverage, and deduplicated assignment failures. The existing UI result acknowledges the response, not assignment success. A manager must inspect accepted dates, current conflicts, role and existing timesheets before completing assignment or deliberately cancelling/replacing the request through the existing workflow. Do not replay an answered link, blindly rerun the RPC, or broaden dates to the live job span. Missing legacy snapshots need manual inspection; the query cannot reconstruct every historical consent window or detect every role mismatch. Dryhire intentionally has no timesheets.

`NOWAIT` failures can also arise from unique-key updates to profiles (including email or `calendar_ics_token`), not only profile deletion. Concurrent cancellation, a missing parent or a deadlock victim can leave the response confirmed without assignment. The inner RPC error and outer catch currently produce `auto_assign_upsert_error` and `auto_assign_error` for one failed attempt. Keep those existing event contracts in this phase and deduplicate alert candidates by request, not event count. New pgTAP assertions also characterize the inherited NULL-role behavior: a legacy offer extension with no `meta.role` clears the department role while preserving membership scope and activating accepted dates. Changing that behavior needs a separate role/pricing decision.
